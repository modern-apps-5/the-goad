The Grandmother of All Demos

GOAD Automation Walkthrough

How the lab gets built, start to finish, without reading any code. Five personas each own one part and hand a defined set of things to the next. Pick a persona and step through their part.

PersonaOwns
The organization, sign-in, capacity, networking, load balancer capacity, and AgentMinder as a core organization tool
Namespaces, Argo CD, Kubernetes clusters, databases, the private AI model, the golden path, and the Tanzu Platform setup the agents run on
The music store's code, and nothing else
The developer for agents: the incident AI agents, their tool servers, and the agents' identities in AgentMinder and which tools each agent may call
Network guardrails in NSX and the web firewall

The idea behind it. Every change starts in git. Terraform builds what has to exist first, and Argo CD keeps everything else matching git. Nobody logs in to a cluster to change things by hand.

Cloud admin

Set up the organization and its shared services

Three stages, each building on the last. A person starts them from GitHub. Each run first shows what it would change, and changes the lab only when the person approves it.

  1. VCF Automation · VCF SSO

    Create the organization

    • A new organization, GOAD, for the whole demo
    • Single sign-on, so people log in with their company accounts
    • How much compute and storage the organization gets, and its networks
    • The Avi load balancer, and a policy for self-service PostgreSQL databases
  2. VCF Automation

    Set up who can do what

    • The platform engineering team from Active Directory becomes admin of the main project
    • A service account the platform engineer's automation logs in as
    • Load balancer capacity for the namespaces to use
    • A Kubernetes cluster for the cloud admin's own tools
  3. AgentMinder

    Run AI agent governance for the organization

    AgentMinder goes on that cluster. It controls which AI agents may call which tools, and records what they do. It is a core organization tool, like sign-in, so the cloud admin owns it. The agentic ops engineer registers their agents in it.

  4. Handoff

    What the platform engineer gets

    • An organization with capacity, networking, load balancing and databases ready to use
    • A login for the platform engineer's automation
    • Nothing more. The cloud admin does not build the app's environments.
Platform engineer

Build the environments, then let Argo CD run them

Terraform builds the starting point and hands it to Argo CD. From then on, a change in git is a change in the lab.

  1. Terraform · VCF Automation

    Build the landing zone

    • Four namespaces: one for the platform itself, one for private AI, one for the music store, and one for the platform tools
    • An Argo CD instance, with read-only access to the GitHub repository
    • An Ubuntu image for the music store's virtual machine
    • A Tanzu Platform space for the agentic ops engineer, connected to the private model and the lab's systems
  2. Secret Store · External Secrets

    Keep secrets out of git

    Passwords and keys live as GitHub secrets. Terraform puts them in the Supervisor's Secret Store. Inside each cluster, External Secrets copies them in where the apps need them.

    GitHub secretto Terraformto Secret Storeto External Secretsto The app
  3. Argo CD

    Hand off to Argo CD

    Terraform tells Argo CD which part of git belongs to which namespace or cluster. After that, Terraform stays out of the way. To change anything inside, someone changes git, and Argo CD applies it.

  4. Argo CD · DSM · VKS · Private AI Services

    Argo CD builds the platform in order

    Argo CD creates things in waves and waits for each wave to be healthy before the next. A database comes up first, then the service that uses it, then the apps.

  5. Handoff

    What the developers get

    • The music store's developers get a running store and a build and deploy path they never set up
    • The agentic ops engineer gets a Tanzu Platform space, the private model, and the incident tools
    • Each team works in its own folder in git and nothing else
Developer on the golden path

From one code change to production

The developer writes code for four services: store, cart, orders and chat. There is no container file, no Kubernetes setup and no pipeline to maintain. The platform engineer owns all of that, the same way for every app.

  1. GitHub

    The developer merges a change

    A reviewed change to the app's code is the only thing the developer does. Everything after it is automatic.

  2. GitHub Actions

    GitHub only starts the build

    GitHub asks the lab to build. Its login can start a build and read the result, and nothing else. The build itself runs inside VCF.

  3. Tekton · Tanzu Hub

    Tekton builds from a trusted base

    • Every image starts from a base image Broadcom builds and maintains, not one from the public internet
    • That base comes through the lab's own registry, which the cloud admin set up
    • One build template, owned by the platform engineer, covers every Python service
  4. Harbor

    Images land in the lab's registry

    Each image is labelled with the code change it came from. Nothing goes to a public registry.

  5. GitHub

    A deploy request proposes the release

    The build opens a pull request that points the app at the new images. Building is not deploying. Every release is reviewed, recorded and easy to roll back.

  6. Argo CD

    Argo CD rolls it out

    When the request is merged, Argo CD starts the new version and retires the old one. Nobody touched the cluster. The music store shows the change.

Agentic ops engineer

Build and run the AI agents that watch the music store

The agentic ops engineer is the developer for agents. They write nine apps on Tanzu Platform that investigate incidents in the music store. The apps are operations tooling, not part of the music store business. The platform engineer owns the cluster and Tanzu setup the apps run on, the same split as with the music store's developers.

  1. From the platform engineer · Tanzu Platform

    A space to run in

    The platform engineer provides the space the apps run in, already connected to the private Qwen model and to the music store's cluster.

  2. From the platform engineer · Argo CD

    Tools for the agents to work with

    Zammad (tickets), Grafana and Prometheus (monitoring) run on the platform tools cluster, apart from the music store they watch.

  3. Terraform · GitHub Actions · AgentMinder

    Each agent gets an identity and its limits

    The agentic ops engineer's Terraform registers each agent and its tool servers in the cloud admin's AgentMinder, and sets which tools each agent may call. They know what each agent needs, so the limits are theirs for now. A person starts the run from GitHub, and it changes AgentMinder only when approved.

    The same run hands each agent its identity on Tanzu Platform and wires each agent to its tools. No agent secret is stored in GitHub.

  4. GitHub Actions · Tanzu Platform

    A workflow deploys the apps

    Any change to the agents or tool servers in git deploys them again. Nobody deploys them by hand. The tool servers hold logins to Avi, Kubernetes and VCF, so they stay with an operations team, not an app team.

    AppIts job
    Incident chatWhere people talk to the agents
    OrchestratorRuns an investigation and calls the specialists
    Three diagnostic agentsSpecialists for the load balancer, Kubernetes and VCF
    Three tool serversThe tools each specialist may use, for Avi, the cluster and VCF
    Privacy filterRemoves personal data from text before it goes anywhere
  5. The result

    A working agentic system inside VCF

    • The agents run on Tanzu Platform, next to the music store they watch
    • They reason with the private Qwen model, which runs in VCF
    • They reach Avi, Kubernetes and VCF only through AgentMinder, and only the tools they are allowed
    • They read from and write to the same Zammad and Grafana people use
Security admin

Guardrails for the network and the web

Like the other personas, the security admin works through Terraform, started from a GitHub workflow. They never log in to the app's cluster. They write firewall rules in NSX, and NSX enforces them inside the cluster.

  1. From the platform engineer · Argo CD · Antrea

    The cluster joins NSX

    When Argo CD builds the music store cluster, it connects the cluster's networking to NSX. NSX can then see the cluster and send it rules.

  2. GitHub Actions · Terraform

    The security admin's workflow runs Terraform

    A person starts the security admin's workflow in GitHub. It runs on the build machine inside the lab and shows what would change in NSX. It changes NSX only when the person approves it. The NSX login is a GitHub secret, and Terraform keeps its record in the same shared place as every other persona.

  3. Terraform · vDefend

    Terraform writes the rules in NSX

    The rules name each music store service and say which traffic is allowed. For example, only the load balancer may reach the store's front end.

  4. NSX · Antrea

    NSX pushes the rules into the cluster

    The rules show up in the cluster as read-only policies. If someone changes them in the cluster, NSX puts them back. Every change goes through the workflow.

  5. Antrea

    Three layers decide every connection

    The cluster checks the layers in order. The first rule that matches wins.

    LayerOwnerWhat it does
    1. GuardrailsSecurity adminCompany-wide rules from NSX. Allow rules only, so the layers below still get a say.
    2. App rulesThe app's teamWhich services in the app may talk to each other
    3. Default denyPlatform engineerBlocks anything the layers above did not allow
  6. The result

    A music store guarded at every layer

    • Avi's web application firewall checks every request before it reaches the cluster
    • NSX guardrails, app rules and a default deny decide every connection inside it
    • All of it comes from git, through a workflow, with no hand-made rules
Under the hood

What keeps the automation consistent

The pieces that make every run behave the same, whoever or whatever starts it.

  1. GitHub Actions · vSphere

    A build machine inside the lab

    GitHub's own machines cannot reach the lab, so the workflows run on machines inside it. Those machines are containers on the Supervisor. Each takes one job at a time and cleans up after it, so no run inherits anything from the last.

  2. Gitea

    One shared record of what Terraform built

    Terraform keeps its record of the lab on the lab's own Gitea server, one record per persona. A lock lets only one run change the lab at a time, and every earlier version is kept. A run from GitHub and a run from a laptop read and write the same record.

  3. Git · GitHub secrets

    Same settings for everyone

    Everything about the lab that is not secret lives in git, so it is the same for every run. Passwords and keys are team values held as GitHub secrets, not personal ones. Because every run uses the same values, one run never undoes another.

  4. GitHub Actions · Argo CD

    Two kinds of change

    • Infrastructure changes are deliberate. Each persona's Terraform runs only when a person starts it, shows its plan, and applies only when approved.
    • App changes flow on their own. New app code starts a build, a change to the agents redeploys them, and Argo CD keeps everything it owns matching git all the time.
  5. Dependencies

    Each layer builds on the one below

    The personas form a chain. The cloud admin's organization comes first, because everything runs inside it. The platform engineer's namespaces, clusters and Tanzu space come next. The agents can only be registered once their space exists, and the security rules can only reach the music store once its cluster has joined NSX. Inside Argo CD, sync waves apply the same idea: a database is healthy before anything that uses it starts.

  6. Argo CD · Supervisor Namespaces

    Everything has one owner

    Each piece of the lab belongs to exactly one persona's Terraform or one Argo CD application, never two. A namespace owns what Argo CD puts in it, clusters included, so removing a namespace removes everything inside. That clean ownership is what lets the whole lab be built, and taken apart, in a predictable order.
